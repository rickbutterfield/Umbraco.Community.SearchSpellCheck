# Upgrade to Umbraco 18

From `17.8.1` to `18.3.1` (tag `release-18.3.1`).
Branch `v18/feature/upgrade-18`, cut from `v18/dev` (`d4ac2b3`, the merged v17 port). `v18/dev`, `v18/main`, `v19/dev` and
`v19/main` were created from the same commit when PR #8 merged.

**Targets CMS release:** `release-18.3.1` (stable, 5 November 2026). The package's own version stays a pre-release
(`18.0.0-alpha`), as `17.0.0-alpha` does on the v17 line.

## Follow-ups

- **Umbraco 19 is a rewrite, not a version bump.** 19.0.0-rc1 removes every Examine type the package builds on (`IIndexRebuilder`, `IndexPopulator`, `UmbracoExamineIndex`, `IUmbracoIndexConfig`, `ContentValueSetValidator`, `BaseValueSetBuilder`, `IndexCreatorSettings`); they move to `Umbraco.Cms.Search.*`, and 18.3.1 marks none of them `[Obsolete]`, so no build warning points at them. Plan `major-upgrade 19` as a port onto Umbraco.Cms.Search.
- The `[Obsolete(... "Scheduled for removal in 2.0.")]` messages in `ISuggestionService.cs:36` and `SuggestionService.cs:230` do not fit version-aligned numbering.
- `BuildOnStartupHandler.cs:62` ignores the `Attempt` that `RebuildIndexAsync` returns; on a cold boot the CMS's own rebuild also rebuilds `SpellCheckIndex`, so it is built twice.
- Carried from the v17 upgrade (not repeated here): protecting a page on a live site keeps its words until a rebuild; the duplicated
  "live content" rule; the older `RebuildOnPublishHandler` faults; `release.yml` tags that never match a pre-release.
- The Clean asset copies dirty the test site tree on every build; decide whether to stop tracking them.
- `metaData.cshtml` favicon path differs from Clean 8.
- `Author.cshtml:12` reads `MainImage` without a null check.
